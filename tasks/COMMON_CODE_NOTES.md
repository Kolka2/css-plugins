# Общий код плагинов — возможный ход (не задание)

> **Это не задание.** Описан один из возможных ходов. Делать ли его, когда и в каком объёме — решает только владелец. Агенту не начинать эту работу без прямой команды владельца и не ссылаться на этот файл как на план.

## Что повторяется

На ноябрь 2026 одни и те же механики написаны в нескольких плагинах отдельно:

| Механика | Где | Как |
|---|---|---|
| Временные квары с восстановлением | `warmup` (`OverrideCvar` / `RestoreCvars`), `nadepractice` (`SetCvarTemporarily` / `RestoreCvars`), `templates/example.sp` | запомнить исходное значение, вернуть при любом выходе |
| Бесконечный раунд | `warmup` — блокирует конец раунда (`CS_OnTerminateRound`) и продлевает часы (`m_iRoundTime`); `nadepractice` — `mp_ignore_round_win_conditions 1` и `mp_roundtime 9` | два разных способа, оба работают на сервере |
| Возрождение | `warmup` — после смерти и раз в секунду для всех мёртвых; `nadepractice` — после смерти, входа в команду, `joinclass` | оба проверяют выбор модели по `m_iClass` |
| Деньги и закупка | `warmup` и `nadepractice` — 16000, восстановление после покупки, закупка везде (`m_bInBuyZone`), `mp_buytime` | одинаково |

Объём небольшой (в `nadepractice` — около 200 строк из 5000), но копии расходятся: проверка или исправление в одной не доходит до другой. Пример: проверка `m_iClass` перед возрождением была подтверждена в `warmup`, а в `nadepractice` долго стояла под `CSS-VERIFY`, пока её не перенесли вручную.

## Почему не «интеграция с `warmup`»

- По правилу 3 раздела 2 `ARCHITECTURE.md` все зависимости необязательны: даже если режим будет запускать разминку и уступать ей, его собственный код для работы без `warmup` останется. Кода станет больше, сочетаний для проверки — вдвое.
- Разминка — фаза перед матчем (таймер, подсказки «разминка», `mp_restartgame` в конце, вето `Warmup_OnEnding`), а не среда для тренировки.
- Пока идёт разминка, возрождением и деньгами владеет она; это конфликтует с возрождением в точке смерти и выдачей режима.
- Отдельный сервис «среда тренировки» с API по тому же правилу 3 тоже не убирает запасной код из потребителей.

## Возможный ход: общие `stock`-функции на этапе сборки

Общий include-файл, который компилируется внутрь каждого плагина (например, `scripting/include/csscommon/*.inc`):

- `cvars.inc` — временные квары с восстановлением;
- `respawn.inc` — «можно ли возродить» (команда, жив ли, выбрана ли модель) и само возрождение;
- `buy.inc` — закупка везде и восстановление денег после покупки;
- `round.inc` — бесконечный раунд, если владелец выберет один способ из двух.

Плюсы: код в одном месте; во время работы плагины друг от друга не зависят; «один владелец» сохраняется (каждый плагин владеет ресурсом сам, пока активен).

Цена и риски:
- нужно правило в `ARCHITECTURE.md`: раздел 6 сейчас говорит, что include-файл — только публичный контракт без логики; общий код — другой вид include-файлов (`stock`, без нативов, форвардов и состояния), это надо оговорить;
- `warmup` уже проверен на сервере вместе с Retakes: после перевода на общий код — повторная проверка. Копию `warmup.inc` в `Kolka2/css-retakes` это не затрагивает (API не меняется), но если Retakes собирается с общими include-файлами — их придётся положить и туда;
- `nadepractice` — повторная проверка возрождения, кваров и закупки;
- изменение общего include-файла пересобирает все плагины, которые его используют (правило «собирай все плагины перед коммитом» уже есть в `CLAUDE.md`).

Возможный порядок, если владелец решит делать: правило в `ARCHITECTURE.md` → общие include-файлы → перевод `nadepractice` (проверка) → перевод `warmup` при его следующей правке (проверка с Retakes) → `templates/example.sp`.
