# Архитектура плагинов CS:S

Правила, по которым пишутся все плагины этого сервера (SourceMod 1.12+, только Counter-Strike: Source). Документ рассчитан и на людей, и на ИИ-агентов: его можно положить в репозиторий и сослаться на него из `CLAUDE.md`.

Шаблоны, проверенные компилятором SourcePawn 1.12, лежат рядом: `templates/example.sp` (сервис), `templates/include/example.inc` (его API), `templates/example_consumer.sp` (плагин с необязательной зависимостью).

---

## 1. Слои

```
Аддоны режима     retakes_standardallocator, retakes_sitepicker, ...
      │  API режима (retakes.inc)
Режимы            retakes, nadepractice, (обычный 5×5 — сама игра)
      │  необязательные зависимости
Сервисы           warmup, match-core, match-control
```

| Слой | Что делает | Примеры |
|---|---|---|
| **Сервис** | Общая механика, нужная разным режимам. Ничего не знает о режимах. | `warmup` — разминка; `match-core` — таймы, OT, счёт, конец матча; `match-control` — `!ready`, паузы |
| **Режим** | Как идёт раунд: кто где появляется, что выдаётся, кто побеждает. | `retakes`, тренировка гранат |
| **Аддон режима** | Подменяемая часть режима через его API. | аллокаторы оружия, выбор сайта, HUD |
| **Утилита** | Не влияет на игру и ни от кого не зависит. | статистика, админ-команды, логирование |

`match-control` — сервис, который использует другие сервисы (`warmup`, `match-core`). Это допустимо, пока нет циклов.

## 2. Правило зависимостей

1. **Зависимости только сверху вниз.** Режим может знать про сервис, сервис про режим — никогда. Аддон знает про свой режим, режим про конкретный аддон — никогда (только про своё API).
2. **Никаких циклов.** Если двум плагинам нужно знать друг о друге, общее выносится вниз, в сервис.
3. **Все зависимости между нашими плагинами необязательные.** Каждый плагин загружается и работает в одиночку: нет `warmup` — режим стартует сразу; нет `match-core` — нет таймов. Обязательная зависимость (`REQUIRE_PLUGIN`) допустима только для аддона от своего режима.
4. **Сторонние библиотеки — только если без них никак.** Две-три функции дешевле написать самому, чем тащить библиотеку.
5. **Без gamedata/DHooks в плагинах сервисов и режимов.** Используем только то, что даёт SourceMod (sdktools, sdkhooks, cstrike). Если без хука движка не обойтись — отдельный необязательный аддон, который может сломаться после обновления игры, не утянув за собой режим.

## 3. Один владелец у каждой вещи

Каждый ресурс игры меняет ровно один плагин. Остальные могут читать, но не менять.

| Ресурс | Владелец |
|---|---|
| Деньги и закупка во время разминки | `warmup` |
| Деньги и оружие во время раунда режима | режим (+ его аллокатор) |
| Смена сторон, счёт команд, конец матча | `match-core` |
| Состав команд каждый раунд | режим (если у него автокоманды); несовместимо с таймами `match-core` |
| Готовность, паузы | `match-control` |
| Квар | тот, кто его изменил (он же восстанавливает) |

Правила:
- В шапке каждого плагина перечислено: **Владеет**, **Читает**, **Использует** (см. шаблон). Если два плагина объявляют владение одним ресурсом — это ошибка архитектуры, её решают до кода.
- Если ресурсом временно должен владеть другой (разминка поверх режима), владелец по умолчанию **уступает**: проверяет состояние сервиса и не вмешивается (`if (IsWarmupActive()) return;`).
- **Квары.** Меняем только через «временную установку» с запоминанием исходного значения и восстанавливаем при **любом** выходе: конец фазы, `OnMapEnd`, `OnPluginEnd`. Чужие квары не трогаем. Игровые пределы матча (`mp_maxrounds`, `mp_winlimit`) — 0, конец матча решает `match-core`.
- **Своё состояние, а не выводы из чужого.** Считаем раунды, фазы и тайм в своих переменных, а не по сумме счёта или значению игрового квара.

## 4. Как плагины общаются

| Механизм | Смысл | Пример |
|---|---|---|
| **Натив** | спросить или приказать | `Warmup_IsActive()`, `Warmup_End()` |
| **Форвард-уведомление** (`void`) | «произошло» | `Warmup_OnEnd`, `Match_OnSidesSwitched` |
| **Форвард с вето** (`Action`, `ET_Hook`) | «можно я?» | `Warmup_OnEnding` → `Plugin_Handled` = «подожди» |

- Форвард-уведомление вызывается **после** того, как состояние изменено, чтобы подписчик видел уже новое.
- Форвард с вето никогда не вызывается при тихой остановке (смена карты, выгрузка).
- Подписчик не должен из форварда вызывать нативы, которые снова вызовут тот же форвард.

### Порядок в событиях игры

Когда несколько плагинов реагируют на одно событие (`round_end`, `round_start`), порядок задаётся слоем:

| Кто | Когда |
|---|---|
| Сервисы, которые **меняют** состояние (смена сторон) | `EventHookMode_Pre` |
| Режимы, которые **реагируют** (подготовка раунда) | `EventHookMode_Post`, а то, что зависит от результата работы сервисов, — в `RequestFrame` |
| Аддоны | из форвардов своего режима, а не из событий игры напрямую |

## 5. Имена и файлы

Имя плагина `<name>` — короткое, латиницей, через `_` или `-`: `warmup`, `match_core`, `retakes`.

| Что | Формат | Пример |
|---|---|---|
| Исходник | `scripting/<name>.sp` | `scripting/warmup.sp` |
| Части большого плагина | `scripting/<name>/*.sp` | `scripting/retakes/teams.sp` |
| API | `scripting/include/<name>.inc` | `scripting/include/warmup.inc` |
| Библиотека | `<name>`, константа `<NAME>_LIBRARY` | `WARMUP_LIBRARY "warmup"` |
| Нативы | `<Name>_Глагол` | `Warmup_IsActive`, `Warmup_End` |
| Форварды | `<Name>_On<Событие>` | `Warmup_OnEnd`, `Warmup_OnEnding` |
| Квары | `sm_<name>_<что>` | `sm_warmup_time` |
| Обязательные квары | `sm_<name>_enabled`, `sm_<name>_debug`, `sm_<name>_version` | |
| Команды игроков | короткие, без префикса, если не конфликтуют | `!ready`, `!guns` |
| Админ-команды | `sm_<name>_<что>` | `sm_warmup_end` |
| Конфиг кваров | `AutoExecConfig(true, "<name>")` → `cfg/sourcemod/<name>.cfg` | |
| Данные | `addons/sourcemod/configs/<name>/` | спавны по картам |
| Переводы | `translations/<name>.phrases.txt` (+ `ru/`) | |
| Cookies | `<name>_<что>` | `retakes_ctriflechoice` |
| Debug-лог | `logs/<name>_debug.log` | |

Части одного плагина (`scripting/<name>/*.sp`) делятся **по ответственности** (подготовка раунда, команды, события, натив-API), а не по размеру. Глобальные переменные, квары и `OnPluginStart` — в главном файле.

## 6. API (include-файл)

- Include описывает **только** публичный контракт: нативы, форварды, константы, `SharedPlugin`. Никакой логики.
- `SharedPlugin` + `__pl_<name>_SetNTVOptional` с `MarkNativeAsOptional` для каждого натива — чтобы зависимость могла быть необязательной.
- Константа `<NAME>_API_VERSION` и натив `<Name>_GetApiVersion()`.
- **Совместимость:** API можно расширять (новые нативы, форварды, необязательные параметры в конце), но нельзя менять смысл и сигнатуры существующих. Ломающее изменение = новая версия API + запись в README.
- У каждого натива и форварда — doc-комментарий: что делает, когда вызывается, что значит возвращаемое значение.

### Подключение чужого API как необязательного

```sourcepawn
#undef REQUIRE_PLUGIN
#include <warmup>
#define REQUIRE_PLUGIN

bool g_bHasWarmup;
public void OnAllPluginsLoaded()             { g_bHasWarmup = LibraryExists(WARMUP_LIBRARY); }
public void OnLibraryAdded(const char[] n)   { if (StrEqual(n, WARMUP_LIBRARY)) g_bHasWarmup = true; }
public void OnLibraryRemoved(const char[] n) { if (StrEqual(n, WARMUP_LIBRARY)) g_bHasWarmup = false; }

bool IsWarmupActive() { return g_bHasWarmup && Warmup_IsActive(); }
```

Все обращения к чужому плагину — только через такие обёртки. Прямой вызов натива без проверки библиотеки — ошибка.

## 7. Обязательное в каждом плагине

**Загрузка**
- `AskPluginLoad2`: проверка `GetEngineVersion() == Engine_CSS`, регистрация нативов и `RegPluginLibrary`.
- `OnPluginStart` обрабатывает позднюю загрузку: обходит уже подключённых клиентов.
- Квары `sm_<name>_enabled`, `sm_<name>_debug`, `sm_<name>_version`; `AutoExecConfig`.

**Надёжность**
- Состояние сбрасывается в `OnMapStart`/`OnMapEnd`, а не полагается на значения глобальных переменных с прошлой карты.
- Всё, что плагин изменил (квары, свойства игроков, сущности), возвращается в `OnMapEnd` и `OnPluginEnd`.
- В таймеры передаётся `userid` (`GetClientUserId`), а не индекс клиента; внутри — `GetClientOfUserId` и проверка на 0.
- Таймеры, которые не должны пережить смену карты, — с `TIMER_FLAG_NO_MAPCHANGE`.
- `Handle`/methodmap-объекты удаляются (`delete`), когда больше не нужны.
- Циклы вида «пока слот не пуст» — с ограничителем итераций.
- Удалённое оружие — не только `RemovePlayerItem`, но и `AcceptEntityInput(weapon, "Kill")`.

**Движок**
- Свойства, в наличии которых в CS:S есть сомнения, проверяются (`HasEntProp`/`FindSendPropInfo`) с одной записью в лог при отсутствии, без падения.
- Всё, что зависит от поведения движка и не проверено на сервере, помечается `// CSS-VERIFY: <что проверить>` и попадает в чек-лист тестов.

**Боты**
- Различать «участник» (человек или бот, играет раунды) и «человек» (чат, меню, cookies, очередь с приоритетом). Две функции, а не одна `IsPlayer`.
- Люди всегда приоритетнее ботов при нехватке мест.
- Число ботов меняет только один плагин (обычно режим), через `bot_quota`.

**Отладка**
- `LogDebug(...)` в `logs/<name>_debug.log` при `sm_<name>_debug 1`: каждое решение, которое плагин принимает (кто куда назначен, почему закончилась фаза, какие квары изменены).

## 8. Стиль кода

- `#pragma semicolon 1`, `#pragma newdecls required`, новый синтаксис, methodmaps (`ConVar`, `GlobalForward`, `StringMap`).
- Отступ 4 пробела, `{` на той же строке.
- Префиксы глобальных: `g_` для переменных, `g_cv` для кваров, `g_fwd` для форвардов.
- Сборка без предупреждений. Неиспользуемые вспомогательные функции — `stock`.
- Тексты для игроков — через переводы (минимум en + ru), не строками в коде.

## 9. Документация и тесты

У каждого плагина:
- `README.md` (или раздел общего README): что делает, слой, квары, команды, API, зависимости, известные ограничения.
- Пункты в `TEST_CHECKLIST.md`: что проверить на сервере, включая все `CSS-VERIFY`.
- Записи в `CHANGELOG` или в сообщениях коммитов при изменении API.

## 10. Чек-лист перед новым плагином

Ответить до того, как писать код (или отдавать задачу агенту):

1. В каком он слое?
2. Чем владеет? Не владеет ли этим уже кто-то?
3. Что читает у других и через какой API?
4. От кого зависит? Зависимости необязательные? Нет ли цикла?
5. Какой API даёт сам: нативы, уведомления, вето?
6. В каком порядке реагирует на события игры относительно других плагинов?
7. Что меняет в кварах и где восстанавливает?
8. Что должен делать с ботами?
9. Что нельзя проверить без сервера (`CSS-VERIFY`)?

## 12. Ограничения и компромиссы

У такой архитектуры есть цена. Ниже — известные минусы и как их сглаживать.

| Минус | Чем грозит | Как сглаживать |
|---|---|---|
| Больше плагинов, API, конфигов | время на инфраструктуру, которая может не понадобиться | правило двух потребителей (ниже) |
| Необязательные зависимости дают много сочетаний | ошибки в сочетаниях, которые редко запускаются | тестировать только реальные конфигурации сервера, перечисленные в `TEST_CHECKLIST.md` |
| Порядок между плагинами держится на соглашении (Pre/Post) | плавающие ошибки, если кто-то нарушил | соблюдать раздел 4; при сомнении — `RequestFrame` у реагирующего |
| Состояние разбросано по плагинам | перезагрузка одного плагина посреди матча ломает согласованность | сервис после загрузки восстанавливает то, что можно (фаза, счёт из игры), и сообщает форвардом «состояние сброшено»; перезагружать плагины между матчами |
| Тихая деградация: забытый плагин просто не работает | нет ошибки, есть странное поведение | отчёт при загрузке (ниже) |
| Опубликованный API трудно менять | ранние ошибки проектирования остаются надолго | API версии 0, пока плагины используешь только ты |
| «Один владелец» соблюдается только среди своих плагинов | игра и сторонние плагины трогают то же самое | изоляция сторонних плагинов (ниже) |
| Без gamedata некоторые вещи делаются хуже | автозакладка бомбы, паузы | хрупкие возможности — в отдельные необязательные аддоны |

### Правило двух потребителей

Механика выносится в отдельный сервис, только когда она нужна хотя бы двум плагинам. До этого она живёт внутри плагина, но изолированно: в своём файле, за своими функциями, чтобы вынести её можно было механически. Пример: готовность и паузы сначала можно сделать частью `match-core`, а отдельный `match-control` выделить, когда готовность понадобится режиму без матча.

### Отчёт при загрузке

Каждый плагин в `OnAllPluginsLoaded` пишет в лог одну строку: версия и какие необязательные библиотеки найдены. Пример: `[retakes] 1.0.0, warmup: yes, match_core: no`. Это дешёвая защита от тихой деградации.

### Несовместимые сочетания

Общей системы проверки конфликтов нет: она усложнила бы каждый плагин и заставила бы сервисы знать о режимах. Вместо неё:
1. **Конфигурацией.** Несовместимые плагины просто не загружаются вместе (на сервере с несколькими режимами — через менеджер режимов, раздел 13).
2. **Точечной проверкой сверху вниз**, только для известных опасных пар. Проверяет плагин верхнего слоя, потому что только он знает о нижнем. Пример: Retakes с автокомандами видит, что загружен `match-core` с включёнными таймами, и пишет предупреждение в лог (или просит `match-core` отключить таймы через его натив). Сервис о режиме при этом ничего не узнаёт.
3. Проверка — **предупреждение в лог**, а не отказ работать, если ошибка не ломает игру.

## 13. Несколько режимов и сторонние плагины

Сторонние плагины (GunGame, Deathmatch, surf-таймеры и т.п.) не используют наш API, и встраивать их в архитектуру не нужно. Их **изолируют**.

- **Режим = набор плагинов + конфиг + пул карт.** Описывается в настройках менеджера режимов (если режимы живут на одном сервере) или отдельным сервером.
- **Смена режима — только вместе со сменой карты.** Старые плагины рассчитаны на запуск при старте карты и при выгрузке посреди карты оставляют квары, хуки и сущности.
- **Базовый конфиг.** Конфиг каждого режима начинается с `exec modes/base.cfg`, который выставляет все важные квары в эталонные значения. Так сторонние плагины не обязаны ничего восстанавливать за собой.
- **Наши сервисы подключаются по режимам.** `warmup` — в Retakes и 5×5; в GunGame не загружается, там респаун даёт Deathmatch.
- **Плагины, загруженные всегда** (админка, статистика, ранги), проверяются на совместимость со всеми режимами сервера.
- Режимы, совсем не похожие на остальные (surf), лучше держать на отдельном сервере.
